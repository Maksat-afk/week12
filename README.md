# Simple Vault — практика Anchor

В проекте реализованы задания с 8-й по 12-ю неделю.

## Что было сделано

1. **Неделя 8 — создание Vault.** Админ создаёт хранилище для SPL-токена. Также пользователи могут создавать свои карточки.
2. **Неделя 9 — депозиты.** Пользователь вносит токены в Vault и получает взамен share-токены.
3. **Неделя 10 — вывод токенов.** Пользователь возвращает shares и получает свои токены обратно. Для этого используется CPI.
4. **Неделя 11 — создание Raydium CLMM-пула.** Скрипт создаёт два тестовых токена и пул на Devnet.
5. **Неделя 12 — обмен через Raydium.** Vault может обменивать TOKEN_A на TOKEN_B и обратно через Raydium CLMM.

## Основные инструкции контракта

```text
initialize_vault  — создаёт VaultState PDA, token account и share mint
create_user_card  — создаёт личную карточку пользователя
deposit           — переводит токены в Vault и выпускает shares
withdraw          — сжигает shares и возвращает токены пользователю

add_pair_token    — добавляет в Vault второй токен TOKEN_B
swap              — обменивает токены Vault через пул Raydium
sync_vault        — возвращает Vault в обычный режим работы
```

Код, который отвечает за работу с Raydium, находится в файле `programs/simple_vault/src/raydium.rs`.

## Как работает Vault

### 1. initialize_vault

Эту инструкцию вызывает админ. Она создаёт три основных аккаунта:

| Аккаунт | Для чего нужен |
|---|---|
| `vault_state` | Хранит информацию о Vault: администратора, mint токена, балансы и другие данные |
| `vault_token_account` | Хранит токены пользователей |
| `share_mint` | Используется для выпуска share-токенов |

Для создания аккаунтов используются PDA (Program Derived Address). Они создаются на основе специальных seeds.

### 2. create_user_card

Каждый пользователь должен сначала создать свою карточку. Она нужна для учёта его депозитов и shares.

В карточке хранятся:

- `vault` — адрес Vault, к которому относится карточка;
- `owner` — владелец карточки;
- `deposited` — количество внесённых токенов;
- `shares` — количество полученных shares;
- `bump` — bump для PDA.

Seeds карточки:

```text
["user_card", vault_state, user]
```

Поэтому один пользователь может иметь только одну карточку в одном Vault. Если попробовать создать вторую, инструкция завершится ошибкой.

### 3. deposit(amount)

С помощью этой инструкции пользователь вносит токены в Vault и получает share-токены.

Сначала контракт проверяет сумму и рассчитывает количество shares. После этого токены переводятся с аккаунта пользователя в Vault, а share-токены выпускаются на его аккаунт.

Формула расчёта:

```text
Первый депозит:
shares = amount

Последующие депозиты:
shares = amount * total_shares / total_tokens
```

Например:

- Пользователь A вносит 100 токенов и получает 100 shares.
- Пользователь B вносит 50 токенов и получает 50 shares.

В результате в Vault находится 150 токенов и выпущено 150 shares.

Важно: перед депозитом пользователь должен вызвать `create_user_card`.

Основные ошибки:

- `ZeroAmount` — сумма равна нулю;
- `SharesTooSmall` — рассчитанное количество shares равно нулю;
- `MathOverflow` — переполнение при расчётах.

### 4. withdraw(shares_amount)

Эта инструкция позволяет пользователю забрать токены из Vault.

Пользователь указывает количество shares, которое хочет вернуть. Контракт рассчитывает соответствующее количество токенов.

Формула:

```text
tokens = shares * total_tokens / total_shares
```

Далее происходят следующие действия:

1. Проверяется количество shares и баланс Vault.
2. С помощью CPI вызывается Token Program и сжигаются shares пользователя.
3. Токены переводятся из Vault на аккаунт пользователя.
4. Обновляются балансы Vault и данные карточки.

Для перевода токенов используется подпись Vault PDA. У PDA нет обычного приватного ключа, поэтому программа подписывает операцию через seeds с помощью `CpiContext::new_with_signer`.

**Что такое CPI?**

CPI (Cross-Program Invocation) — это вызов одной программы из другой. В нашем проекте контракт обращается к Token Program, чтобы выполнять перевод, выпуск и сжигание токенов.

Основные ошибки:

- `ZeroAmount` — указано нулевое количество shares;
- `VaultEmpty` — в Vault нет shares;
- `WithdrawTooSmall` — за указанное количество shares получается ноль токенов;
- `MathOverflow` — переполнение при расчётах.

## Неделя 11 — создание токенов и пула Raydium

На этой неделе задача заключалась в создании собственного CLMM-пула на Raydium Devnet.

**Коротко о CLMM**

CLMM — это пул ликвидности, в котором пользователь может выбрать определённый ценовой диапазон для своих токенов. Это отличается от обычного пула, где ликвидность распределяется по всему диапазону цен.

В рамках этой недели используется скрипт:

```text
scripts/create-clmm-pool.ts
```

Он выполняет следующие действия:

1. Создаёт два тестовых SPL-токена: `TOKEN_A` и `TOKEN_B`.
2. Выпускает по 1 000 000 токенов каждого вида на кошелёк.
3. Получает настройки пула из Raydium SDK.
4. Создаёт CLMM-пул с начальной ценой 1:1.
5. Сохраняет адреса токенов и пула в `devnet-pool.json`.

Файл `devnet-pool.json` добавлен в `.gitignore`, потому что у каждого пользователя будут собственные адреса токенов и пула.

### Запуск скрипта

Перед запуском нужно настроить Solana CLI на Devnet и иметь SOL для оплаты транзакций.

```bash
yarn install
yarn create-pool
```

После выполнения скрипта в консоли появятся адреса созданных токенов и пула.

Проверить пул можно через [Solana Explorer](https://explorer.solana.com/?cluster=devnet), выбрав сеть Devnet.

## Неделя 12 — обмен через Raydium CLMM

На этой неделе Vault получил возможность обменивать свои токены через Raydium.

Раньше все токены хранились в Vault в виде TOKEN_A. Теперь можно добавить TOKEN_B и использовать пул для обмена между ними.

### add_pair_token

Эту инструкцию вызывает админ. Она добавляет второй токен в Vault и создаёт для него отдельный token account.

В `VaultState` сохраняются:

- `token_mint_b` — mint второго токена;
- `vault_token_account_b` — аккаунт Vault для TOKEN_B.

Второй токен добавляется один раз.

### swap

Инструкция `swap` выполняет обмен токенов через Raydium CLMM.

Можно обменять:

- TOKEN_A на TOKEN_B;
- TOKEN_B на TOKEN_A.

Для этого используется CPI-вызов `swap_v2`.

Основные параметры:

- `amount_in` — количество токенов для обмена;
- `min_amount_out` — минимальное количество токенов, которое Vault должен получить;
- направление обмена задаётся через `a_to_b`.

Параметр `min_amount_out` нужен для защиты от проскальзывания. Если обмен не может обеспечить минимальное количество токенов, транзакция откатывается.

Также в проекте предусмотрена возможность передать `u64::MAX` вместо `amount_in`. В таком случае контракт использует весь баланс входного токена.

### Проверка пула

Перед обменом контракт проверяет, что пул действительно работает с токенами TOKEN_A и TOKEN_B.

Если передан пул с другой парой токенов или перепутаны аккаунты хранилищ пула, операция завершается ошибкой `WrongPool`.

Для обмена также нужны дополнительные аккаунты Raydium, включая tick arrays. Они передаются через `remaining_accounts`. В тестах для их получения используется Raydium SDK.

### Что происходит с депозитами во время обмена

Когда Vault выполняет обмен, он переходит в режим `in_market`.

В этом режиме `deposit` и `withdraw` временно недоступны. Это сделано для того, чтобы не рассчитывать доли пользователей, пока часть средств находится в другом токене.

После обмена TOKEN_B обратно в TOKEN_A можно вызвать `sync_vault`.

### sync_vault

Эта инструкция возвращает Vault в обычный режим.

Перед синхронизацией контракт проверяет:

- что Vault находится в режиме `in_market`;
- что на аккаунте TOKEN_B нет остатка;
- что нет открытой позиции.

После проверок обновляется `total_tokens` по реальному балансу TOKEN_A, а режим `in_market` отключается.

Если на аккаунте остался TOKEN_B, появится ошибка `TokenBNotZero`.

Чтобы не оставлять небольшие остатки TOKEN_B, можно обменять весь баланс обратно в TOKEN_A и вызвать `sync_vault` в рамках одной транзакции.

## Требования для запуска

Для работы с проектом нужны:

| Инструмент | Версия |
|---|---|
| Rust | stable |
| Solana CLI | 1.18 или новее |
| Anchor CLI | 0.31.1 |
| Node.js | 18 или новее |
| Yarn | 1.x |

Также понадобятся зависимости Anchor, Solana и Raydium SDK.

## Быстрый запуск

### 1. Установка зависимостей

Перейти в папку проекта и установить пакеты:

```bash
yarn install
```

### 2. Сборка контракта

```bash
anchor build
```

После сборки основные файлы появятся в папке `target/deploy/`.

- `simple_vault.so` — собранная программа;
- `simple_vault-keypair.json` — keypair программы. Его нельзя публиковать на GitHub.

### 3. Настройка Devnet

```bash
solana config set --url devnet
solana address
solana balance
```

Команда `solana address` показывает публичный адрес кошелька, а `solana balance` — его баланс.

### 4. Пополнение кошелька

Для работы в Devnet нужны тестовые SOL. Их можно получить через faucet:

[https://faucet.solana.com](https://faucet.solana.com)

Также можно попробовать команду:

```bash
solana airdrop 2
```

Иногда запросы ограничиваются из-за лимитов Devnet.

### 5. Деплой программы

Если программа ещё не развёрнута в Devnet:

```bash
anchor deploy --provider.cluster devnet
```

Деплой отправляет транзакции и требует SOL. Перед выполнением нужно проверить Program ID и настройки кошелька.

### 6. Запуск тестов

```bash
yarn test
```

**Важно:** тесты этого проекта работают с Devnet и могут создавать аккаунты, токены и пулы, а также отправлять транзакции. Поэтому перед запуском нужно проверить настройки сети и баланс кошелька.

Сборка через `anchor build` и проверка TypeScript через `corepack yarn tsc --noEmit` не заменяют полноценный запуск тестов в Devnet.

## Частые ошибки

| Ошибка | Возможная причина |
|---|---|
| `Insufficient funds` | На кошельке недостаточно SOL |
| `AccountNotInitialized` | Аккаунт ещё не создан или программа не развёрнута |
| `ZeroAmount` | Указана нулевая сумма |
| `VaultEmpty` | В Vault нет shares |
| `SharesTooSmall` | Слишком маленький депозит |
| `InMarket` | Vault находится в режиме обмена |
| `TokenBNotZero` | На аккаунте Vault остались токены TOKEN_B |
| `WrongPool` | Передан неправильный пул или аккаунты пула |
| `Unauthorized` | Инструкцию вызвал не администратор |
| `TooLittleOutputReceived` | Обмен не обеспечивает минимальный выход |
| `429 Too Many Requests` | Devnet RPC ограничил количество запросов |
